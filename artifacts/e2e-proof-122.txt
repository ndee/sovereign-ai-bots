What #122 reported
  Subject-scope filtering was honored by the unit/e2e stubs but silently
  SKIPPED on the live classification path (the real `scan` loop). A
  subject-scoped content rule therefore also matched the message BODY, so
  out-of-scope mail was mis-classified.

How this run exercises the LIVE path (not a stub)
  Real email is submitted over SMTP -> Proton Bridge -> the node's own
  `sovereign-mail-sentinel-scan` timer (forced to 1 min for the run) ->
  classification -> mail-sentinel state (zoneHistory / alerts) -> Matrix
  RED alert in the operator's Element room. No stub, no mock: the same
  scan/contentHaystack/determineZone code path the product runs.

Scenarios (cucumber, run id e2e-1780680824150)  — 2/2 passed, 14/14 steps
  1. IN-scope: marker "subjecthit-<runId>" in the SUBJECT, low-signal body.
     Rule: content, scope=subject, contains subjecthit-<runId>, min-zone RED.
     RESULT: classified RED; alert attributed to the subject rule
             (policyModifiers = ["e2e:subject-policy subject e2e-1780680824150"]).
             -> the subject haystack matched on the live path.  PASS

  2. OUT-of-scope: SAME-shaped marker "subjectmiss-<runId>" in the BODY ONLY,
     subject is marker-free ("Weekly status digest <runId>").
     Rule: content, scope=subject, contains subjectmiss-<runId>, min-zone RED.
     RESULT: NOT escalated. Stayed at the model's own AMBER baseline
             (reason: "Routine status update with no action required and no
             deadline" — the LLM's own reasoning, NOT an e2e:subject-policy
             reason), and NO RED alert was recorded.
             -> the subject rule did NOT leak into the body.  PASS

  The asymmetry between #1 and #2 — identical rules differing only in whether
  the marker sits in the subject vs the body — is the #122 guarantee: a
  subject-scoped rule matches the subject and only the subject on the live path.
